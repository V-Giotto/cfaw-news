# CFAW News 后续开发时间线

制定日期：2026-10-14。建议起点：2026-10-15。

目标：优先算法岗位，其次 Agent / LLM 应用开发岗位。主线是“面向个人目标的时序证据检索与判断更新”，首个算法贡献聚焦目标/约束/历史感知重排器。所有日期、数据量和交付内容都是计划，不代表已经实现或测得。

## 投入与当前起点

建议先规划 24 周，至 2027-03-31。按每周 30–40 小时有效投入估算，共约 720–960 小时；时间充足时将额外投入用于标注复核、基础学习、重复实验与真实运行。若 Python、机器学习或 PyTorch 基础薄弱，允许增加 4–8 周学习，并与数据、工程任务交叉。

当前起步版已有独立 FastAPI/React、BM25、26 条归档、不可变证据与引用校验、用户决定/批准、取消与版本保护。DeepSeek 的配置适配通过 20 项本地测试；截至本计划没有真实 DeepSeek 成功调用的验收记录。GitHub 仓库已建立。当前三组种子评测只验证指标和排序管线，不能算算法成绩。

## 各阶段执行重点

### 第 1–2 周：让研究对象清楚且可测

- 第 1 周：完成 DeepSeek 真实接入，记录模型、请求时间、usage、费用口径、结构校验与引用校验结果；为鉴权、限流、超时、输出截断制定可定位的错误类型。
- 第 2 周：定义每步输入、可见证据、上一轮事实、用户约束和合理决策集合。手工构造重复报道、条件补充、冲突、更正/撤回、证据不足等轨迹。
- 开发样例用于调试与规范讨论，不计入最终留出测试。先支持离线评测 CLI，使算法实验不依赖浏览器。

### 第 3–6 周：数据、回放与评测

- 第 3 周：保存发布时间、首次发现时间、抓取时间与内容版本；建立来源和事件分组。今天抓取的旧网页不能仅凭旧发布日期进入历史时刻。
- 第 4 周：完成标注试点和复核。分别标注主题相关性、条件适用性、证据价值、支持/反驳方向以及判断变化。可靠反驳可能是高价值证据。
- 第 5 周：实现 Recall@K、MRR、nDCG@K、变化判断 macro-F1、claim 支持率、硬约束违规率、重复提醒率；保存每样本预测与依据。
- 第 6 周：冻结规范和切分规则；交付 BM25 基线与失败分析。PostgreSQL/Alembic 在此阶段并行推进，保持业务唯一键、事务、快照与批准校验。

主实验数据继续扩充，建议目标为 300–500 条轨迹、约 1,000–3,000 个步骤，以及约 5,000–20,000 篇合法可用候选文档。这是工作量估算，应根据试点标注速度、复核质量和学习曲线调整；同一轨迹的多个步骤不视为相互独立。

20–30% 试点样本争取双人独立标注并仲裁；只有一人时采用间隔后的盲重标，并明确缺少独立标注的限制。LLM 只作预标注辅助。新闻全文的发布权限逐源核对，优先分享元数据、标注、许可允许的短引用和采集脚本。

### 第 7–10 周：建立强对照

- 第 7 周：固定 embedding 模型与版本，实现精确向量搜索和 BM25 对照。
- 第 8 周：实现 RRF，在同一候选/数据范围内评估 Hybrid；先记录真实瓶颈，再决定是否需要 HNSW。
- 第 9 周：加入通用 CrossEncoder，固定相同候选池；查询应包含合理的目标/约束/历史信息，避免给自研方法额外信息造成不公平比较。
- 第 10 周：冻结主实验测试集、语料、索引、prompt、预算和评测配置，产出分组结果与质量—成本曲线。测试集只用于约定的最终比较，不用于选模型、阈值或挖负样本。

数据库和向量检索选 PostgreSQL + pgvector 一套深入。ANN 的相对精确搜索召回与相关性 Recall@K 分开报告。首次可投递的应用开发版本在此形成：有产品、基线和评测，但仍按已完成能力表述。

### 第 11–16 周：形成首个算法成果

核心研究问题：同样的文档、用户信息、生成模型和预算下，经过任务训练的重排器，能否更好地选出适用且影响本轮判断的证据？

- 第 11 周：训练一个小型模型、打通数据到权重到评测的全链路；基于实测显存和耗时决定训练规模。
- 第 12 周：对比分类/成对排序目标，建立随机与困难负样本策略；只用训练数据挖负样本。
- 第 13 周：加入目标约束、旧事实和候选时间条件，保持输入与通用基线公平。
- 第 14 周：做去掉约束、去掉历史、去掉困难负样本等消融；记录上下文长度与训练成本，避免只因更多 token 得益。
- 第 15 周：做学习曲线、重要配置的多随机种子实验、按事件家族聚类的置信区间；复核效果最差的样本组。
- 第 16 周：完成训练与对照报告、模型卡、复现命令和算法版简历素材。

强基线和自研方法的候选池、可见信息与下游生成模型一致。模型排名提升与最终判断提升分别报告。使用 DeepSeek 等滚动模型别名时保存日期、请求/响应模型标识、服务端版本指纹（如有）与响应缓存；对比尽量在接近的时间交错进行，明确无法完全固定服务端权重的限制。

不预先许诺“提升 10%/20%”。没有稳定提升时，检查标签、训练规模、目标和分组表现，记录负结果；可接受质量相近但成本更低的成果，但必须按实际证据表述。

### 第 17–20 周：将算法放进受限 Agent

- 第 17 周：单独评测重复、补充条件、事实变更、矛盾、更正和撤回；对比无历史、摘要历史、结构化事实历史。
- 第 18 周：实现有界工具与停止动作，对比固定 Top K/固定补证和简单不确定性策略。全文仅在相应工具返回后对策略可见，失败调用也计预算。
- 第 19 周：引入 LangGraph 的状态、持久化 checkpoint 与人工中断/恢复；数据库保存长期业务事实。MCP 在内部工具稳定后作为小范围接口扩展。
- 第 20 周：完善 Redis/Celery、周期触发与事务发任务；验证重复投递、worker 退出、审批后崩溃、取消与重启。记录并抑制重复提醒/重复行动。

队列重试或图 checkpoint 本身不等于业务操作恰好执行一次。外部副作用和批准写入需要独立幂等设计。持续跟踪需要周期触发器及幂等调度，不能只有 worker。

若第 16 周算法实验仍存在实质问题，这一阶段优先保留确定性流程，将复杂动态策略延后，集中解决算法证据不足的问题。

### 第 21–24 周：真实运行与求职交付

- 第 21 周：完成 Linux/Docker Compose 的实际部署、健康检查、日志/trace、配置与数据库备份恢复；启动前瞻运行。观测平台选 Langfuse，并保留本地导出。
- 第 22 周：持续记录成功率、错误类别、耗时分布、实际 token 用量与费用；做来源失效、限流、prompt injection、越权工具参数和恢复测试。
- 第 23 周：邀请另一位开发者依文档运行，处理复现问题；完成产品演示和算法报告，整理个人贡献与上游来源。
- 第 24 周：结束首段 14–21 天运行报告，发布经过验证的版本和复现说明，形成算法/应用两版简历材料。

真实运行从第 1 周起持续采集基本记录，最后阶段形成集中报告；它不能替代独立测试集。项目可以继续迭代，同时开始投递。

## 每周投入与基础学习

建议约 55% 时间用于数据、训练、实验和误差分析，30% 用于可运行系统与验证，15% 用于论文/源码阅读、文档和表达。每周输出一个可演示结果或实验结论、一份失败记录和下周待验证的问题。

基础随任务补齐：第 1–2 周重点是 Python 类型/异常/asyncio/HTTPX；第 3–6 周是 SQL、事务、索引、评测指标和基础统计；第 7–10 周是 embedding、BM25、RRF、ANN；第 11–16 周是 PyTorch、反向传播、排序损失、训练/验证/测试与实验设计；第 17 周后是状态机、幂等、恢复、Linux 和部署。

数据结构与算法、SQL、数学和英文阅读建议每天固定练习。只把堆/哈希/检索索引等适合项目的问题落到项目中，其余通过独立练习巩固。

模型调用、标注和 GPU 费用单独设预算；时间不限不代表计算资源无限。早期可用 CPU 和固定服务，训练前先做小批次显存/速度探测。优先单个重排器训练；大模型 SFT/RL、多 Agent 协作、浏览器/Computer-use 和自建推理 Infra 暂不作为 24 周交付依赖，后续依据岗位与实验瓶颈选择。

## 四个求职节点

- 第 6 周：有任务定义、数据规范、可复现 BM25 和工程闭环，能作为进行中的研究项目展示。
- 第 10 周：有检索对照和独立运行产品，可开始用应用开发版本投递。
- 第 16 周：有训练、消融、分组误差分析与可复现报告，更适合作为算法方向核心项目；是否取得提升按实测填写。
- 第 24 周：增加真实运行、部署与外部复现证据，完善技术深度和交付可信度。

每个节点保存 release notes、固定配置、报告和可验证数据；只在用户授权时向远端推送或发布。
