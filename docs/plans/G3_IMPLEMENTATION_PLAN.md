> **状态：提案 / 待项目所有者批准**
>

## 1. 目标与项目现状

### 1.1 G3 的目标

G3 在 G2
已经生成的情报候选之上，构建一个**可冻结输入、可历史回放、可解释、可复现、可比较**的个性化排序器。它回答：

-   在某个历史时点，某个用户当时有哪些情报候选可见？
-   根据当时已知的用户兴趣、历史展示和明确反馈，哪些事件更值得优先呈现？
-   在 180 / 420 / 900 秒等阅读预算下，如何分配重点情报和前沿速览？
-   为什么某个事件被提升、降权、保留或截断？
-   与简单时间排序、词法相关性及历史感知基线相比，P1
    是否带来可重复的改善？

G3 的核心交付是离线排序与评测能力，不是一个新首页，也不是实时服务。

实施前必须重新检查当前 `main` 分支及其提交。此前已确认的设计基线包括：

-   [G2 发布说明](../G2_PUBLICATION.md)：G2

### 1.3 G2 与 G3 的责任边界

G2
负责将可见文档转化为事件级、证据可追踪的情报候选，包括事件身份/版本、情报内容、证据束、候选层级、来源覆盖及生成谱系等信息。

G3
负责在不改变这些事实的前提下，依据用户画像、历史交互、时效、实质变化和阅读预算决定呈现顺序与计划。

G3 **不得**： - 改写 G2
的事实、引用、证据归属、来源独立性、事件谱系或不确定性； - 把 `hold`
候选仅因用户相关性高而升级成普通重点情报； - 把
`included`、`rendered`、`opened` 和 `acknowledged`
合并成同一个"已读"状态； -
将未来文档版本、未来用户反馈、未来画像或事后标签泄漏到历史回放； -
将合成测试期望、AI 开发复核或 Mock 结果描述为真人研究或真实用户效果； -
修改 G1/G2 冻结数据、契约或历史验收报告来使 G3 通过。

## 2. 范围与非目标

### 2.1 G3 范围内

1.  建立独立 `evals/intelligence_g3/` 包和版本化契约。
2.  从 G2 PR6 的正式交接对象建立严格适配器，不重新实现 G2 事实生成。
3.  建立不可变 Persona 快照和追加式历史交互事件。
4.  在同一候选池上运行可比较的排序基线与 P1。
5.  对 1 / 3 / 7
    天回访、重复曝光、实质变化、更正/撤回和未知覆盖进行回放。
6.  将排序和阅读预算分开，输出重点情报/前沿速览计划及未展示原因。
7.  生成可复现的运行工件、指标、分母、失败案例、成本与限制。
8.  保持 G1/G2 只读，保留旧应用回归测试。

### 2.2 明确不在 G3 范围内

-   不迁移生产数据库，不改变 SQLAlchemy 业务表。
-   不接入 React 首页、API、SSE 或新的在线用户流程。
-   不增加真实 LLM 调用、Embedding 服务、外部 API 或付费推理。
-   不新增新闻来源或采集器，不改变 G2 输入之外的采集行为。
-   不引入向量数据库、独立任务队列、LangGraph 或多 Agent 框架。
-   不训练新的学习排序模型；先验证可解释规则是否有效。
-   不发邮件、推送通知、不自动执行用户行动。
-   不把 G3 的离线通过描述为真实用户效用或生产就绪。

如实施中发现上述事项确有必要，先提出单独
ADR（决策记录）、成本/风险和替代方案，等待项目所有者明确批准。

## 3. 设计原则

1.  **先契约，后算法。**
    输入/输出、时间语义和身份映射没有冻结前，不调权重。
2.  **事件级对比。** G3 应消费 G2 事件级候选；不能重复合并事件，也不能把
    G2 的去重收益记到 G3 排序算法名下。
3.  **时间可见性是硬约束。** 所有特征都只能使用 `as_of` 时点可见的信息。
4.  **历史语义显式。**
    被纳入、被渲染、被打开、被明确了解和被忽略是不同事实。
5.  **证据与排序分离。** 分数只决定呈现顺序，不提高事实可信度。
6.  **预算独立。**
    先计算排序，再按可解释策略分配预算；不得靠固定条数假装满足阅读时间。
7.  **同输入、同输出。**
    随机种子、配置、算法版本、输入清单和代码指纹均需记录。
8.  **失败要可诊断。**
    输出未展示原因、覆盖缺口、指标分母和不可计算原因。
9.  **最小增量。** 每个 PR
    只承担一个可审查的职责；不为未来可能需要的架构创建空壳。
10. **诚实报告。**
    合成数据上的成功只证明开发检查，不证明真实用户或真实来源的泛化。

## 5. 核心契约设计要求

具体字段必须先核对 G2 PR6 的实际 Pydantic 类型，再确定 G3
schema；以下是语义要求，不是要求机械照抄字段名。

### 5.1 `G3ReplayInput`

至少绑定： - G2 输入运行/manifest 身份及其 SHA-256； -
`timeline_id`、`step_id`、`as_of`； - 本时点可见的候选事件及其 G2
事件身份/版本； - 当时可见的 Persona 版本； -
本时点以前的历史交互事件； - 来源覆盖状态与观察时间； -
阅读预算与已注册实验配置。

校验必须拒绝重复
ID、未知引用、未来时间、输入集合不一致、未注册配置及缺少可信外部 pin
的清单。不能在预测时从未受信任的 manifest 自行计算"可信 pin"并据此放行。

### 5.2 Persona 快照

推荐字段语义： - 稳定的本地 persona ID 与不可变版本 ID； -
`available_at`； - 显式领域兴趣、当前目标和硬约束； -
用户明确声明已知的内容； - 探索偏好； - 本次阅读预算； - 来源/创建方式及
provenance。

画像只允许使用 `available_at <= as_of`
的版本。不要从单次打开行为推断用户已经掌握某项知识。第一版以明确兴趣为主，不做复杂的长期隐式画像学习。

### 5.3 追加式历史交互

至少区分： - `included`：服务端纳入某次简报； -
`rendered`：客户端确认实际展示； - `opened`：用户打开详情； -
`acknowledged`：用户明确表示已了解； -
`dismissed`：用户明确忽略/暂时不想看； -
显式反馈：有帮助、不相关、已知或其他受 schema 约束的反馈。

每条记录需有唯一 ID、事件/情报版本引用、发生时间、来源、关联 delivery 和
provenance。历史记录追加保存，不允许原地覆盖来伪造过去状态。更正/撤回反馈应通过新事件表达。

语义规则： - `included` 不等于 `rendered`。 - `rendered` 不等于
`opened`。 - `opened` 不等于 `acknowledged`。 - 只有明确的
`acknowledged`
或有明确定义的显式反馈，才可以作为"用户声明已知"的信号。 -
历史惩罚不能压过安全/证据约束或重大更正、撤回和实质更新。 -
当事件合并/拆分时，映射必须显式且可审计；不确定映射不能静默合并用户历史。

### 5.4 排序输出与预算计划

每个候选输出至少应能追溯： - event key / revision 和代表性 G2
情报引用； - 排名、原始分数及分数组件； - 算法
ID、配置版本和历史特征来源； - 计划 tier（如 `focus` / `radar`）； -
估计阅读秒数； - 是否被呈现、截断或保留在候选中； -
未展示/降权的结构化原因； - 与来源覆盖、不确定性和证据约束相关的诊断。

排序结果不得把 G2 的 `tier_candidate` 原样伪装成 G3 的最终个性化
tier；两者应分别保存。

## 6. 排序方案与公平比较

### 6.1 基线与 P1

优先复用 `evals/intelligence_v1/` 的现有实现和语义。每个 G3
算法都必须使用**同一个 G2 事件候选池、同一个 `as_of`、同一 Persona
快照、同一历史快照和同一预算**进行比较。

-   **B0：时间基线。**
    按当时可见的最新实质材料/既定时效规则排序，规则需版本化。
-   **B1：词法相关性基线。** 复用现有 BM25/Persona query
    机制；不得读取未来文本或 Gold 标签。
-   **B2：事件级身份/重复控制基线。** G3 输入已由 G2
    聚合到事件级时，不得再重复做事件合并。若事件合并收益需要评估，必须在单独的端到端对照/消融中报告，不能记为
    G3 排序增益。
-   **B3：时间加权基线。**
    在明确相关性/基础分数上加入可解释、版本化的时间衰减。
-   **B4：历史感知基线。** 在 B3 上加入符合历史语义的曝光/明确反馈规则。
-   **P1：事件价值排序。**
    在同一候选池上组合显式兴趣相关性、新颖性、证据约束下的实质变化、时效、历史重复惩罚和受限探索。

如既有 G1 B0--B4 的具体语义与上述 G3 事件级输入不完全一致，应在
`bridge.py` 或 ranker adapter 中明确差异并保留版本号；不能悄悄更改 G1
的算法实现来匹配 G3。

### 6.2 P1 的初始设计

可以采用可解释的加权框架：

\[ S = w_rR + w_nN + w\_{`\Delta`{=tex}}`\Delta `{=tex}+ w_tT + w_xX -
w_dD \]

其中： - (R)：与显式兴趣、当前目标和硬约束的相关性； - (N)：对该 Persona
的新颖性； - (`\Delta`{=tex})：有证据支持的实质变化； - (T)：时效； -
(X)：探索奖励； - (D)：无实质增量的重复曝光惩罚。

这只是初始实验假设，不是已验证的最优公式。权重、归一化、缺失值策略、时间半衰期、探索上限必须写入注册配置并记录版本。不可让高相关性抵消
G2 的 `hold` 或其他硬约束。

### 6.3 历史与事件身份处理

-   按 `as_of` 选择可见历史，拒绝未来曝光/反馈。
-   事件版本变化不能自动意味着新事件；必须使用 G2 提供的事件谱系。
-   更正、撤回和重大约束变化需要在回访时重新提升，不能被普通重复惩罚压下去。
-   同一事件多篇转载不能因为多个文档而获得多份独立性奖励。
-   对事件拆分/合并后的历史继承，使用显式映射及置信/不确定状态；不确定时应保守处理并输出诊断。
-   来源覆盖为 `unknown`、`partial`、`failed` 或 `service_offline`
    时，不能把"未发现更新"解释为"确认没有更新"。

## 7. 阅读预算与 Focus / Radar 分配

排序和预算是两个不同阶段。

1.  先生成完整事件排名。
2.  根据已注册预算策略分配 Focus 和 Radar。
3.  计算预计阅读时间，保留完整的截断/未展示原因。
4.  保证重要更正、撤回和其他硬约束候选不会被探索奖励或普通历史惩罚挤掉。
5.  保留完整候选集供 Archive/Library 层使用；未进入简报不等于删除资料。

建议沿用 G1 已注册的 180 / 420 / 900 秒预算进行第一轮对比。Focus/Radar
的预算比例可以作为实验参数（例如
60/40、70/30、80/20），但这些只是候选实验配置，不是预先决定的产品默认值。最终配置应由离线结果和所有者审查决定。

阅读时间估计必须有明确的、可复现的规则，并报告估计与真实阅读时间尚未校准的限制。不能声称预算精确反映真实认知时间。

## 8. 指标、实验和统计报告

### 8.1 必须报告的指标

-   `ImportantEventRecall@budget`：阅读预算内命中的重要事件数 /
    可评估的重要事件总数。
-   `ImportantMissRate`：遗漏重要事件数 / 可评估的重要事件总数。
-   `nDCG@K`：按事件级参考相关性/重要性计算，并说明 K 与分母。
-   `DuplicateExposureRate`：重复事件占据的展示位置或曝光比例，定义必须固定。
-   `RevisitCoverage@1d/3d/7d`：对应回访窗口内仍然重要且可评估的事件被呈现比例。
-   `MaterialChangeRecall`、`CorrectionRecall`、`WithdrawalRecall`：分别报告可评估数量、命中数和未定义原因。
-   `RadarCoverage` /
    `Diversity`：独立事件数、领域覆盖和来源类型覆盖，避免只用文章数充当广度。
-   `ReadingCost`：计划阅读秒数与预算使用率。
-   `Evidence/coverage diagnostics`：引用可追踪、证据约束违规、来源覆盖未知/失败时的错误解释。
-   `Latency/Cost`：仅报告实际测量的耗时与资源；没有真实模型调用时，不得编造
    Token 或模型费用。

### 8.2 统计和数据限制

-   所有比率同时报告分子、分母、样本数和 `undefined_reason`。
-   同一事件家族内样本相关，若样本量允许，使用 family-level
    bootstrap，而不是把转载/重复状态当独立样本。
-   合成 fixture、AI 开发期望和独立测试材料分开报告。
-   不把同一批数据反复调参后的最好结果描述为独立泛化结果。
-   没有足够独立事件家族时，明确报告"样本不足/无法估计"，不强行给显著性结论。
-   P1 未稳定优于 B4 时，保留 B4，不强行选 P1。

### 8.3 建议的对照实验

固定候选池、Persona、`as_of`、预算和参考标签，至少运行： 1. B0 / B1 / B3
/ B4 / P1 的同池对照。 2. 去除历史特征。 3. 去除新颖性/实质变化特征。 4.
去除探索奖励。 5. 去除重复曝光惩罚。 6. 180 / 420 / 900 秒预算敏感性。
7. 1 / 3 / 7 天回访窗口。 8.
事件版本更新、更正、撤回和覆盖未知等对抗案例。

B2 的事件合并收益应单独作为 G2/端到端消融，不混入 G3 排序的增益归因。

## 9. PR 计划与 Definition of Done

### PR1 --- 契约、适配器和时间可见性

**目标：** 建立 G3 最小骨架，并严格消费 G2 正式交接对象。

**工作内容** - 审查 G2 PR6 的实际输出 schema、版本、字段、provenance 和
manifest 机制。 - 定义 G3 输入/输出契约与版本化 schema。 - 实现

pin、配置版本和父运行指纹。 - 添加 `as_of`、未来 Persona、未来历史、重复
ID、未知引用、候选集不一致等测试。 - 写
README，明确离线运行方式与数据边界。

**验收标准** - G2
输入字段不被静默丢弃；任何允许丢弃/投影字段都有文档解释。 -

只有契约和适配器，没有生产数据库/前端/模型集成。 -

**停止条件：** 若 G2→G3
必需语义缺失或字段含义不清，停止实现算法，先提出问题与候选方案。

## 10. 每个 PR 的通用流程

每个 PR 必须按以下顺序执行：

1.  **实现前审计**：阅读 `AGENTS.md`、本计划、相关 G1/G2
    文件和测试约定；输出将修改的文件与不变量。
2.  **最小实现**：仅实现当前 PR 范围，不提前实现后续 PR。
3.  **测试**：运行当前 PR
    测试及相关回归；优先使用仓库现有环境，不擅自安装依赖或联网。
4.  **自审**：检查时间泄漏、引用完整性、证据边界、数据指纹和兼容性。
5.  **交付记录**：总结改动、实际执行的命令及退出码、测试结果、未完成项和风险。
6.  **独立审查**：使用 `G3_CODEX_PROMPTS.md` 对应的 PR
    审查提示词；审查者先报告问题，不直接掩盖或顺手重构。
7.  **修复与复审**：修复阻断项后重新运行受影响测试，并再次审查。
8.  **所有者批准**：PR 只有在明确审查通过后才进入下一阶段。

任何审查都不得只依据 Codex 自己的总结或声称的测试结果；应检查实际
diff、测试文件、执行输出和工件。

## 11. 总体验收门槛与 Go/No-Go

### 工程门槛（全部必须通过）

-   时间可见性、身份、引用、输入 pin 和配置版本校验通过。
-   历史事件语义严格，追加式记录可审计。
-   G2 的事实、证据和不确定性不被改写。
-   阅读预算、未展示原因与来源覆盖诊断完整。
-   可复现工件完整，缺失/不匹配工件会使验收失败。
-   G1/G2 冻结文件无改动，旧业务回归测试通过。
-   没有未经批准的模型、数据库、前端、采集或依赖变更。

### 算法门槛（报告并评估，不预设必胜）

-   P1 与 B4 等强基线在共同候选池上比较。
-   指标分母、事件家族数、数据来源和限制均透明。
-   重要事件遗漏、更正/撤回误压、重复曝光和预算截断有明确错误分析。
-   如果 P1 没有稳定改善，允许结论为"尚无证据支持替换 B4"。

### G3 结束时应交付

-   `evals/intelligence_g3/` 独立离线实现；
-   版本化 schema、冻结 manifest 与可复现命令；
-   自动化测试与完整验收工件；
-   基线对比、消融、失败案例与限制报告；
-   给 G4 的接口说明和待决策清单；
-   明确说明尚未接入真实数据库、前端和真实用户反馈。
